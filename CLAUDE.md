## Project overview

Nomi: a local-first AI video creation workbench. Electron + React 18 + Tailwind 3 + Zustand + React Flow (`@xyflow/react`) + Vercel AI SDK. Main modules: project library → creation (text) → generation canvas (node system) → timeline preview → MP4 export. Design system: `Design.md` + `src/design/`, token-only, light / dark, density first.
Every change starts from the latest `origin/main` on its own task branch / worktree and is delivered through a PR; pushing to `main` directly is forbidden. Touch files by absolute path, and put new worktrees next to the repository directory.

`pnpm run gates` is the layered pre-commit gate (tiered by risk, sharing `scripts/validation-policy.mjs` with CI); `pnpm run gates:full` is the full tier; the rest of the commands are in `docs/engineering/commands.md`. Start a task with `pnpm run delivery:preflight`.

## Core principles

**P0 Write only what is ours alone** — write by hand only the domain itself (storyboard, shot and production flow, canvas, assets, per-shot spend semantics; `docs/engineering/self-written.json` is the authoritative domain list); general capabilities default to adopting an existing framework / library / standard, and self-written ones must be registered with a reason that counts only as a domain constraint; capabilities are designed for the general case, not coupled to any specific vendor; facts the environment / engine already reports (install paths, model lists, plan scopes) must not be hardcoded or hard-scoped, always read them from the owning system. Ask yourself: "Is this ours alone? No → find something existing first."

**P1 Adding new means deleting old** — a new implementation deletes the old one in the same commit; no parallel version, no fallback; CSS lives only in component `className`, global CSS may only shrink. When one file is modified for a bug a third time within 14 days, a third special-case branch is about to appear, or one change requires reading two bypass paths, stop patching: choose patch / rewrite / delete and write a characterization test first (RW, exercised on 10-15).

**P2 Fix the root cause, not the symptom** — for any bug, regression, CI / platform failure, before touching code follow `.agents/skills/root-cause-remediation/SKILL.md`: separate symptom / direct cause / class root cause, first run `node scripts/door-map.mjs <symbol or file>` to count every entrance, and fix at the earliest shared boundary. Ask yourself: "Can the same class of problem come back through another caller, vendor, version, platform, or old data?" If you cannot answer "no", it is not solved.

**P3 All green is not done** — before reporting a user-visible change complete: reconcile item by item against the approved sample, and Read the real screenshots with your own eyes (both zh and en tracks); a feature delivery needs a real task loop closed; with no real resources record `unverified`, and never let a mock green light stand in for it.

**P5 Think it through before acting** — write a design card (`docs/engineering/design-card.md`) before acting: every change fills the ★ 5 cells (1, 2, 3, 4, 9); changes touching spend / long-running / interruptible / new-surface fill all 9; put it in the task brief or `docs/plan`, and link or inline it in the PR body under `## 设计卡` (design card); the four categories above also need an independent acceptance line before merge, with the PR body carrying `## 独立验收` (independent acceptance) plus the report link and acceptance-line number (which must not be the implementation line). For UI changes first read `docs/design/nomi-design-system.md`, produce an experienceable sample, and get the user's sign-off; when changing existing UI, look at how it really looks first; important changes get one batch grill round first (every question with a default answer, connected surfaces as their own question), pure bug fixes do not.

## Rules

The rule registry of record is `docs/engineering/rules.json` (readable view `rules.md`; every legacy R# number resolves through `aliases`, checked by `check:rule-aliases`). Only 12 rules are resident (level=always): the P0 P1 P2 P3 P5 above (P5 contains the design card and independent acceptance rules) + the status words, parallel discipline, and multi-session rules below + the two judgment principles the user pinned resident on 2026-10-02 (decision autonomy, deciding for the user; execution point manual); everything else is looked up in `docs/engineering-rules.md` only when triggered.

**Status words have exactly four levels**: 已实现未推送 (implemented, not pushed) / 已推送待合入 (pushed, awaiting merge) / 已合入待验证 (merged, awaiting verification) / 已解决 (resolved — requires merge-SHA verification; authorized GitHub CI waivers use the local receipt in `docs/engineering/delivery-and-review.md`).

**Parallel discipline**: a clean task branch in an independent sibling worktree runs `delivery:preflight` first, and a new worktree runs `pnpm install` first; do not switch branches / commit / resolve conflicts inside the shared main repository; before pushing, integrate the latest `origin/main` (merge — no reset, no squashing commits), push only the task branch and open a PR; never force-push; for review / salvage branches compute the merge-base first.

**Multi-session**: one coordinator; only it talks to the user and merges. Workers announce concepts before acting, queue conflicts, open PRs and report numbers; send new issues/decisions with recommendations and costs to the coordinator, without task cards or user questions. Local CI must pass. Merge after a clean pre-merge scan and green GitHub CI; only explicit user permission may waive GitHub CI, recorded in the PR with scope, reason and local evidence. Never waive local CI or fabricate remote checks. At most 3 merges may await receipts; a red receipt stops merging for the user's fix/rollback decision. Keep about 3 implementation sessions. Details: orchestration playbook §19.

## Decision autonomy

By default, drive all the way to the end and leave no leftovers: finish every problem you find, and for anything with a reasonable default, do the version the user would pick and report afterwards. Stop only for key decisions: product direction / irreversible trade-offs / architectural forks / resources only the user has (ask only for product-level quota, large amounts, or irreversibility) / two approved samples that contradict each other (stop and report here; do not pick one yourself and implement it) — for these, gather one round, give a comparison table and a recommendation. Implementation details, naming, module split, test strategy, and evaluation / verification-class spend are yours to decide; report afterwards what it cost.

**When deciding for the user**: ① Start from the creator's real friction and structural constraints, not from an implementation or feature list — first ask where the creator is stuck in that moment, how tired they are; cut by default anything that makes the creator read more, configure more, or learn more; then locate it in the value chain / moat and ask whether one person can carry it; constraints are strategy, so cut or defer speculative big bets first. ② Trace the first-principles "why" to the bottom: claims need evidence, and when unsure, actually check; before calling something a bug, understand why the existing design was written that way; explain a plan in plain words — why, what will happen, what the experience is — and name the one core thing the user has to weigh in a single sentence; if the user cannot repeat back the "why" and "what I am weighing", rewrite it. ③ Ruthlessly minimal plus honest delivery: cut everything that is not worth the fight, and mark gaps and limits plainly. ④ Decide fast when the logic is clear: what the user wants is a partner who dares to analyze, dare to push back, and dare to judge — not a yes-man; the user's own ideas are also just opinions, so push back when they deserve it; "what do you think" means they want your judgment.
